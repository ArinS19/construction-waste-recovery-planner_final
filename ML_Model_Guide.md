# ML Model Guide

Practical, day-to-day guide to the trained model that powers `/api/analyze`.
For the full technical specification (feature schema, response contract,
architecture diagram) see
[ML_MODEL_INTEGRATION_SPECIFICATION.md](./ML_MODEL_INTEGRATION_SPECIFICATION.md).
For where the project currently stands, see
[CURRENT_STATUS_AND_NEXT_STEPS.md](./CURRENT_STATUS_AND_NEXT_STEPS.md).

## 1. Current model

A trained model already ships in this repository:

```
backend/app/ml/saved_models/waste_recovery_model.joblib
backend/app/ml/saved_models/model_metadata.json
```

It is a `scikit-learn` `Pipeline` (`ColumnTransformer` + `RandomForestClassifier`)
trained on the bundled reference dataset at
`backend/app/ml/data/sample_waste_dataset.csv` (3,000 rows, 600 per pathway,
generated by `backend/app/ml/generate_sample_dataset.py`). Reported validation
accuracy is in `model_metadata.json` (currently ~98.7%).

That reference dataset is **synthetic** — it is generated from the same
domain heuristics (condition/contamination thresholds, material-specific
repair/rot/rust logic) that the original rule engine (`backend/app/rules/`)
encodes, not from real inspected construction sites. It exists so the ML
pipeline has *something* labelled to train on and is genuinely useful for
demonstrating the architecture end-to-end, but a model trained only on it
will mostly reproduce those heuristics rather than learn anything the rule
engine didn't already know. Treat it as a bootstrap, not a ground truth.

The three CSVs under the top-level `datasets/` folder
(`Waste_Management_and_Recycling_India_cleaned.csv`,
`Waste_Management_India_20K_cleaned.csv`,
`Waste_Management_with_Extra_Features_cleaned.csv`) are **not** used to train
this model. They are city/municipal-level waste statistics (tons/day,
recycling rate, landfill capacity, etc.) with no per-item `material`,
`condition`, `contamination`, or `recommended_pathway` fields — see
`datasets/README.md` for why they don't fit this schema. They're kept for
reference/future feature engineering (e.g. regional recycling-rate priors),
not as a drop-in training set.

## 2. Replacing the model with real data

When you have real, labelled construction-waste assessment data:

1. Build a CSV with these columns (see
   [ML_MODEL_INTEGRATION_SPECIFICATION.md §2](./ML_MODEL_INTEGRATION_SPECIFICATION.md#2-defined-input-feature-schema)
   for exact value ranges):
   ```
   material, condition, contamination, unit, quantity, broken_percentage,
   condition_score, contamination_score, has_cracks, structural_compromised,
   has_rust, has_rot, is_moist, has_hazardous_coating, is_separable,
   recommended_pathway
   ```
2. Train (from the project root, either OS):
   ```bash
   # Linux/macOS (after ./run_backend.sh has created backend/venv at least once)
   source backend/venv/bin/activate
   python backend/app/ml/train_template.py --dataset path/to/your_data.csv
   ```
   ```cmd
   :: Windows (after run_backend.bat has created backend\venv at least once)
   backend\venv\Scripts\activate.bat
   python backend\app\ml\train_template.py --dataset path\to\your_data.csv
   ```
3. This overwrites `backend/app/ml/saved_models/waste_recovery_model.joblib`
   and `model_metadata.json` in place. No backend or frontend code changes
   are required — restart the backend and it picks up the new model
   automatically (`GET /api/ml/status` confirms `is_user_trained_model_loaded: true`
   and the new `version`/`accuracy`).
4. Re-run the test suite (`pytest backend/tests -q`) to confirm the API
   contract and safety guardrails still hold with the new model.

## 3. Retraining on the bundled synthetic set

To regenerate the sample dataset and retrain from scratch:

```bash
python backend/app/ml/generate_sample_dataset.py   # rewrites sample_waste_dataset.csv
python backend/app/ml/train_template.py             # retrains + overwrites the .joblib
```

`backend/app/ml/cv_test.py` runs a 5-fold cross-validation comparison across
RandomForest/GradientBoosting/DecisionTree/LogisticRegression on the same
dataset if you want to sanity-check model choice before committing to one in
`train_template.py`.

## 4. Safety guardrail (always active, model-independent)

Regardless of what the model predicts, `backend/app/ml/model_adapter.py`
forces `DISPOSAL / SPECIALIZED HANDLING` and
`professional_assessment_required = true` whenever contamination is
`High`/`Hazardous` or a hazardous coating flag is set. This override cannot
be trained away by a future model — it is applied after inference, not
learned.
